# Quantum Oracle — архитектура on-chain синхронизации и серверных расчётов

**Дата:** 18 сентября 2026  
**Версия:** 3.0  
**Модель:** блокчейн — источник состояния; интерфейс читает состояние напрямую из сети; сервер выполняет расчёты и отправляет команды исполнения.

---

## 1. Главная концепция

Quantum Oracle состоит из трёх рабочих слоёв:

1. **Блокчейн** — хранит балансы игроков, ставки, историю ставок, раунды, результаты, выплаты и настройки интерфейса.
2. **Сервер расчётов** — получает события из блокчейна, рассчитывает результаты ставок и формирует команды для исполнительного Oracle-контракта/модуля.
3. **Frontend** — читает данные непосредственно из блокчейна и содержит лёгкий локальный runtime-пиксель: небольшой вычислительный модуль, который формирует локальное облако интерфейса.

Блокчейн остаётся единственным источником истины для пользовательского состояния. Сервер не является базой данных и не хранит баланс или историю как отдельную систему.

> В этой версии слово «Oracle» означает исполнительный слой расчётов/команд. Это не внешний ценовой оракул и не отдельный источник истины для балансов игроков.

## 3. Что хранится в блокчейне

### 3.1 Балансы игроков

Баланс игрока не дублируется в серверной базе. Варианты хранения:

- нативный баланс сети;
- баланс игрового токена;
- депозит/escrow в `QuantumOracleCore`;
- доступный баланс и заблокированная сумма.

Для UI используются view-функции контракта и события `BalanceUpdated`, `Deposit`, `Withdrawal`.

### 3.2 Ставки и история

Каждая ставка фиксируется транзакцией и событием:

```solidity
struct Bet {
    uint256 betId;
    uint256 roundId;
    address player;
    uint256 amount;
    int16 direction;
    uint256 createdAt;
    BetStatus status;
    uint256 payout;
}

enum BetStatus { Open, Won, Lost, Cancelled, Paid }
```

История читается интерфейсом из событий и публичных методов контракта. При необходимости серверный индексатор может ускорять чтение, но не меняет данные и не считается источником истины.

### 3.3 Раунды

```solidity
struct Round {
    uint256 id;
    uint256 startBlock;
    uint256 closeBlock;
    uint256 settlementBlock;
    uint256 totalPool;
    RoundStatus status;
    bytes32 resultHash;
}
```

Время и блоки должны фиксироваться сетевыми параметрами. Для денежных расчётов предпочтительнее использовать номер блока или подтверждённый settlement window, а не локальные часы браузера.

## 4. Server Calculation Layer

Сервер нужен только для вычисления и отправки команды, а не для хранения пользовательского состояния.

### 4.1 Обязанности сервера

1. Подписаться на события `BetPlaced`, `RoundClosed`, `ConfigUpdated`.
2. Получить полное состояние раунда из блокчейна.
3. Рассчитать outcome и сумму выплаты по детерминированному алгоритму.
4. Сформировать `settlementCommand`.
5. Подписать команду серверным ключом исполнения.
6. Отправить её в `SettlementExecutor`.
7. Дождаться подтверждения транзакции и проверить emitted events.
8. Повторить команду безопасно при сетевой ошибке благодаря `nonce` и `commandHash`.

### 4.2 Команда расчёта

```solidity
struct SettlementCommand {
    uint256 roundId;
    bytes32 stateRoot;
    bytes32 resultHash;
    uint256 totalPayout;
    uint256 nonce;
    uint256 deadline;
    bytes signature;
}
```

Контракт должен проверить:

- подпись разрешённого расчётного сервера;
- уникальность `nonce`;
- соответствие `roundId` и текущему состоянию раунда;
- отсутствие повторного settlement;
- срок действия команды;
- лимиты выплат и доступность средств.

### 4.3 Что запрещено серверу

- менять баланс напрямую;
- редактировать историю ставок;
- подтверждать неподписанные команды;
- использовать отдельную БД как замену блокчейну;
- принимать результат, не подтверждённый транзакцией.

## 5. Smart contracts

### `QuantumOracleCore`

Основной контракт:

- депозиты и выводы;
- балансы игроков;
- создание раундов;
- размещение ставок;
- хранение истории;
- блокировка средств;
- применение settlement-команды;
- начисление выплат;
- on-chain настройки локального облака.

### `SettlementExecutor`

Исполнительный контракт:

- whitelist расчётных серверов;
- проверка подписи;
- replay protection;
- вызов settlement в `QuantumOracleCore`;
- журнал команд и ошибок.

### `CloudConfig`

Настройки визуального runtime, доступные всем интерфейсам:

```solidity
struct CloudConfig {
    bool enabled;
    uint16 particleCount;
    uint16 spread;
    uint16 intensity;
    bytes32 version;
}
```

Конфигурация не содержит секретов и не влияет на денежную логику. Она нужна только для одинакового формирования локального облака во всех интерфейсах.

## 6. Local Pixel Runtime

Каждый frontend содержит небольшой статический модуль `QuantumPixel`.

### Назначение

- загружается вместе с интерфейсом;
- читает `CloudConfig` из блокчейна;
- строит локальное облако частиц/визуальный слой;
- синхронизирует версию конфигурации с сетью;
- не хранит приватные ключи и балансы;
- не отправляет пользовательское состояние на сторонний API.

### Принцип работы

```text
1. Frontend получает CloudConfig из контракта.
2. QuantumPixel создаёт локальное облако в памяти браузера.
3. UI читает баланс, ставки и историю через RPC/indexer.
4. При событии ConfigUpdated Pixel пересобирает облако.
5. При изменении on-chain состояния UI обновляет только соответствующий слой.
```

Пиксель можно сделать отдельным npm-пакетом или встроенным модулем. Для безопасности его следует считать визуальным runtime, а не частью финансового доверенного контура.

## 7. Frontend

### Основные компоненты

```text
app/
├─ page.tsx
├─ components/
│  ├─ BalancePanel.tsx          # баланс из blockchain
│  ├─ BetForm.tsx               # транзакция ставки
│  ├─ BetHistory.tsx             # события и история ставок
│  ├─ RoundChart.tsx             # состояние текущего раунда
│  ├─ SettlementStatus.tsx       # on-chain статус расчёта
│  └─ QuantumPixel.tsx           # локальное облако
├─ lib/
│  ├─ contracts.ts
│  ├─ blockchain-reader.ts
│  └─ cloud-config.ts
└─ abi/
   ├─ QuantumOracleCore.json
   └─ SettlementExecutor.json
```

### Источник данных UI

| Данные | Источник |
|---|---|
| Баланс | `QuantumOracleCore` / token contract |
| История ставок | events `BetPlaced`, `BetSettled`, `PayoutClaimed` |
| Раунд | `QuantumOracleCore.getRound()` |
| Результат | on-chain settlement event |
| Статус сервера | on-chain `SettlementSubmitted` / `SettlementConfirmed` |
| Облако | `CloudConfig` в блокчейне |

Frontend не должен считать подтверждённым ни один результат, пока нет подтверждённой транзакции сети.

## 8. Потоки данных

### Ставка

```text
Игрок → транзакция placeBet()
     → QuantumOracleCore сохраняет ставку и блокирует средства
     → BetPlaced event
     → сервер видит событие
```

### Расчёт

```text
Раунд закрыт
→ сервер читает состояние из blockchain
→ рассчитывает outcome
→ подписывает SettlementCommand
→ отправляет команду в SettlementExecutor
→ контракт проверяет подпись и nonce
→ QuantumOracleCore начисляет payout
→ SettlementConfirmed event
→ интерфейс читает новый баланс из blockchain
```

### Синхронизация облака

```text
Администратор вызывает setCloudConfig()
→ CloudConfigUpdated event
→ все интерфейсы читают новую конфигурацию
→ каждый локальный QuantumPixel пересобирает облако
```

## 9. Безопасность

- Серверный ключ имеет только роль `SETTLEMENT_ROLE`, без доступа к пользовательским средствам.
- Административные функции защищены multisig.
- Для команд обязательны nonce, deadline, domain separator и chain ID.
- Все выплаты выполняются pull-моделью или строго проверяемым settlement.
- Контракты используют `ReentrancyGuard`, checks-effects-interactions и OpenZeppelin SafeERC20.
- Результат рассчитывается детерминированно из on-chain state.
- Не хранить приватные ключи в frontend, local pixel или браузере.
- Провести unit, invariant, fuzz и fork-тесты до mainnet.
- Открыто публиковать ABI, адреса контрактов и версии алгоритма settlement.

## 10. Этапы реализации

### Этап 1 — контракты

1. Реализовать `QuantumOracleCore`.
2. Добавить `Bet`, `Round`, `Balance`, `SettlementCommand`.
3. Реализовать `SettlementExecutor` и роли.
4. Добавить `CloudConfig`.
5. Написать unit/invariant/fuzz-тесты.

### Этап 2 — расчётный сервер

1. Подключить чтение событий через RPC.
2. Реализовать детерминированный settlement engine.
3. Добавить очередь команд и nonce manager.
4. Подписывать команды в защищённом runtime.
5. Реализовать повторную отправку и reconciliation по событиям сети.

### Этап 3 — frontend

1. Подключить чтение контрактов и событий.
2. Вывести баланс и историю напрямую из сети.
3. Реализовать транзакции депозита, ставки и вывода.
4. Добавить отображение settlement status.
5. Встроить локальный `QuantumPixel`.
6. Читать и применять `CloudConfig`.

### Этап 4 — тестовая сеть

1. Развернуть контракты в testnet.
2. Проверить полный цикл bet → calculate → settle → payout.
3. Проверить повторную доставку команды.
4. Проверить отказ сервера и восстановление.
5. Проверить синхронизацию нескольких интерфейсов.

### Этап 5 — mainnet

1. Провести аудит контрактов.
2. Настроить multisig и ротацию settlement key.
3. Установить лимиты раундов и выплат.
4. Включить мониторинг транзакций и балансов.
5. Запустить ограниченную beta-версию.

## 11. Затраты и ресурсы

### Команда

- 1 Solidity/blockchain engineer;
- 1 backend engineer для settlement server;
- 1 frontend engineer;
- 1 security reviewer/auditor;
- multisig-оператор или технический администратор.

### Инфраструктура

| Ресурс | Назначение |
|---|---|
| RPC provider | чтение сети и отправка транзакций |
| Settlement server | расчёты и подписывание команд |
| Secrets manager/HSM | защита settlement key |
| Monitoring | контроль блоков, событий и ошибок |
| Vercel или аналог | frontend deployment |
| Blockchain explorer | проверка транзакций |

RPC и frontend не заменяют блокчейн и не являются базой состояния.

### Ориентировочная оценка

| Работа | Оценка |
|---|---:|
| Core + escrow + balances | 10–15 dev-days |
| SettlementExecutor и подписи | 5–8 dev-days |
| Расчётный сервер | 7–12 dev-days |
| Frontend blockchain reads/writes | 7–12 dev-days |
| QuantumPixel и CloudConfig | 2–4 dev-days |
| Тестирование и security review | 10–20 dev-days |
| **Итого до testnet** | **~41–71 dev-day** |

Ежемесячные расходы зависят от сети и нагрузки: hosting settlement-сервера, RPC, мониторинг, секрет-хранилище и gas. Основной переменный расход — транзакционные комиссии сети; отдельная база для балансов и истории не требуется.

## 12. Итоговая модель

```text
Blockchain = состояние, балансы, ставки, история, результаты, выплаты, настройки
Server     = расчёт + подписанная команда исполнения
Frontend   = прямое чтение blockchain + отправка пользовательских транзакций
Pixel      = локальное лёгкое облако, управляемое on-chain конфигурацией
```

Такой подход исключает отдельную базу балансов, отдельную базу истории и внешний ценовой источник. Единственная серверная функция — детерминированно рассчитать settlement и передать подписанную команду в блокчейн, где она окончательно проверяется и фиксируется.

Перед запуском необходимо отдельно проверить юридическую модель ставок, требования к лицензированию, KYC/AML и ограничения конкретной юрисдикции.
